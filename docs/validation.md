# Validation and current evidence

This page records what is checked for this checkout and what the checks can prove. A passing generator test proves the generated bytes and installer behavior described by that test; it does not prove that a vendor host will load or execute every generated feature.

## Fast local checks

The unit and integration suite uses temporary local fixtures and does not need external network access (the HTTPS Git case uses a loopback-only server):

```sh
.venv/bin/python -m unittest discover -s tests -v
```

It covers source parsing, all four renderers, resource and executable-file preservation, build ownership, installer receipts, updates, uninstall, conflict handling, the five bundled authoring skills, and the local eval runner contract. The same suite is configured in [`.github/workflows/ci.yml`](../.github/workflows/ci.yml) for Python 3.9, 3.11, and 3.13.

The CI workflow is configured to build a wheel and install it into a fresh temporary virtual environment. `scripts/check_distribution.py` is a standard-library-only smoke check run with `python -I`; it verifies that `any_harness` does not resolve from the checkout's editable `src/any_harness` directory, that its import path matches installed distribution metadata, that the installed CLI places all five bundled authoring skills in a temporary project for each harness, and that the packaged eval CLI can validate and preview a temporary suite. The package's declared runtime dependencies are installed into that temporary environment; no global environment is changed.

To reproduce that packaged check locally:

```sh
smoke_root=$(mktemp -d)
python3 -m pip wheel . --no-deps --wheel-dir "$smoke_root/wheel"
python3 -m venv "$smoke_root/venv"
"$smoke_root/venv/bin/python" -m pip install --no-cache-dir "$smoke_root/wheel"/any_harness-*.whl
"$smoke_root/venv/bin/python" -I scripts/check_distribution.py
```

The temporary directory can be removed after the command completes. Windows uses the corresponding `Scripts` paths.

## Git distribution check

The real HTTPS Git end-to-end check in `tests/test_git_e2e.py` serves a temporary bare repository over a loopback-only HTTPS server. It exercises ref resolution and the CLI's source-folder installation path without contacting a public Git host. The test requires `git`, `openssl`, and local socket access, and it is included by the default unittest discovery command:

```sh
.venv/bin/python -m unittest discover -s tests -p 'test_git_e2e.py' -v
```

## Native format and host evidence

The evidence has these separate levels:

- **Generated format:** all four adapters are rendered and inspected by the local unit/integration tests. The generated Codex marketplace/plugin manifest also passed the locally available Codex plugin-creator manifest validator. That validator is a local tool contract and is not claimed to represent every Codex release.
- **Eval runner orchestration:** `tests/test_eval_contracts.py` uses a deterministic fake `codex` executable to exercise public `eval validate`, `preview`, `run`, and `report` commands, fresh fixture staging, suite-level executable graders, JSONL parsing, missing-harness `skipped` results, inconclusive aggregate status, and malformed-result errors. These are mocked orchestration checks, not model evaluations.
- **Official documentation:** the format and installation research in [`docs/research/`](research/) was checked against the official Claude Code, OpenAI Codex, OpenCode, and Cursor documentation on September 5, 2026. Documentation evidence supports the adapter choices and stated feature gaps; it is not a runtime test.
- **Codex native read-only check:** with Codex CLI 0.153.4, the optional `scripts/check_codex_native.py` check starts `codex app-server --stdio`, sends only `initialize`, `skills/list`, and `plugin/read` requests, and matches each response by request ID. It locally passed for discovery of all five installed authoring skills and for reading all five skills from the generated Codex marketplace package. It does not install a plugin, start a model turn, or execute an agent. Generated files are temporary; the app-server inherits the user's normal Codex environment and may write its ordinary runtime cache or logs.
- **Bounded Codex behavioral smoke:** on September 5, 2026, Codex CLI 0.153.4 ran one copied review-kit case with `--config inherit`, model `gpt-5.4-mini`, effort `low`, sandbox `read-only`, one repeat, one job, and a 60-second timeout. The native process exited 0 after 5.079954 seconds; `output_contains: change-reviewer` and `unchanged: .` passed. The result was **inconclusive** because no native skill-selection event was observable; observed model and effort were `null`, tokens were `input_tokens=14751`, `cached_input_tokens=3328`, `output_tokens=99`, `reasoning_tokens=25`, `cache_write_tokens=0`, and cost was `null`. The source revision was unavailable (`null`) because the smoke ran before the initial commit, and inherited configuration fingerprints were incomplete, so this is a bounded behavior sample rather than a fully reproducible benchmark.

Run the optional Codex check only when the Codex CLI is installed:

```sh
.venv/bin/python scripts/check_codex_native.py
```

The script is not part of default CI because it depends on a particular host CLI and protocol. It terminates the app-server after the read-only requests and kills it if it does not exit within the bounded cleanup wait.

The app-server check uses Unix pipe polling and is intended for macOS or Linux. It uses the normal Codex configuration and runtime directories, so review that scope before running it.

Full native host loading remains unverified for Claude Code, OpenCode, and Cursor. Agent execution, model behavior, hooks, MCP servers, permissions, and other vendor-specific runtime semantics remain unverified for every target, including Codex. The generator preserves explicit native escape hatches, but those settings still require validation in the target host.

The eval runner's process-group timeout cleanup and executable grader examples
are validated on POSIX hosts only. Windows uses an immediate-process timeout
fallback, and POSIX shebang/executable-bit graders require a Windows-specific
implementation before they can be considered portable. Generator and
installer Windows paths are covered separately by their existing tests.
